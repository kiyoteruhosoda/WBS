# ADR-0037: 外のカレンダー（Google・Outlook など）は iCalendar を読み取り専用で取り込む

- 状態: 承認
- 日付: 2026-10-02

## 背景

持ち主の依頼（2026-10-02、task #196）: 「カレンダーを Google や Outlook と同期したい」。会話で次が決まった。

- 会社の Outlook は Microsoft 365 で、Entra ID のアプリ登録（Microsoft Graph の API 連携）は許可が下りない。
  Google の API 連携（OAuth の機密の権限）も、自分用に使うには審査かテスト扱いの 7 日ごとの再認可が要る
- 欲しい向きは **外 → WBS** だけ（WBS の予定を外へ出す必要は無い）
- 中身はどれも iCalendar（.ics）。Google の「iCal 形式の非公開アドレス」・Outlook の「予定表の公開」の ICS・
  従来の Outlook の「予定表の保存」で書き出したファイル。**サービスごとに分けず、入れ方は URL かファイルだけ**でよい
- URL は「知っていれば誰でも読める」秘密。Outlook の公開に不安がある。**URL を続けて読むか（購読）は選べる**ように
  し、購読しないなら URL を保存しない（読み込んだ後すぐ公開を止められる）

## 決定

- カレンダーの種類に **`IMPORTED`（取り込んだカレンダー）** を足す（`calendars.kind`）。表示の選択・組み合わせ
  （ADR-0027）は予定のカレンダーと同じ一覧で使う。WBS の予定は入れられない（422）。仕事 / プライベート
  （ADR-0033）は持たない（計画に数えないのはプライベートと同じだが、区別の切り替えは要らない）
- **入れ方は 2 つだけ**（`FeedSource`）: ファイル（中身を本文で送る）か URL。URL は `subscribe` で購読を選ぶ。
  - 購読しない: 1 回読み、URL は保存しない
  - 購読する: URL を **AES-GCM で封じて**保存し（`calendar_imports.feed_url_sealed`）、15 分ごとに読み込み直す。
    画面には手掛かり（ホスト名と末尾のファイル名だけ。例 `calendar.google.com …/basic.ics`）しか返さない
  - 封じる鍵は**場所で持つ**（`CALENDAR_FEED_KEY_FILE`、k8s の Secret）。鍵の無い配備は購読できない
    （422 `subscription_unavailable`。1 回だけの URL とファイルは使える）。定期の係も起動しない
- **読み込むたびに丸ごと入れ替える**。繰り返し（RRULE・RDATE・EXDATE・この回だけの変更）は読み込むときに
  今日の 92 日前〜400 日先で展開し、回ごとに `calendar_imported_occurrences` に持つ（5,000 回まで）。
  `STATUS:CANCELLED` は持たない。Windows のタイムゾーン名（Outlook）と `X-WR-TIMEZONE`（Google）は読み替え、
  ゾーンの無い時刻は利用者のタイムゾーンとみなす。読むのは `icalendar` ＋ `recurring-ical-events`
- 新しい入れ方で入れ直すと、購読はその入れ方のものに置き換わる（ファイル・購読しない URL で入れ直せば購読は止まる）
- 購読の読み込みに失敗したら、**中身は前のまま**にして理由（`last_error`）を覚える。画面は理由を言葉にして出す
- URL を読むのはサーバーだけ。**内側へ向けさせない**: https（`webcal` は https に読み替え）だけ、宛先の
  アドレスが全世界向けでなければ断る（転送の先も 3 回まで確かめる）、10 MB・20 秒まで。URL はログに出さない
- **取り込んだ回は予定の回（`/calendar/occurrences`）と別に引く**（`GET /api/calendars/imported-occurrences`）。
  計画（予定した時間）・締め・打刻の既定のタスク・通知は予定の回の一覧を見るので、取り込んだ回は入らない。
  画面はカレンダーと「今日」で予定の回の形に直して重ねる（`is_imported`）
- **読み取り専用**: 画面は動かさない・消させない。押すと中身（日時・場所・どのカレンダーか）と「元のカレンダーで
  直す」とだけ出す
- 消すと、読み込んだ回と読み込みの状態（購読の URL）も消える（中の予定を既定へ移す処理は無い）

## 理由

- API 連携（Graph・Google Calendar API）は、会社のテナントの許可と OAuth の審査が要り、繰り返しの例外と
  両側の書き換えの衝突も扱うことになる。欲しいのは外 → WBS の一方向で、見て避けられれば足りるので、iCalendar の
  読み込みで十分。中身の形が共通なので、サービスの区別を持たない方が口が少ない
- 予定の表（`calendar_events`）に混ぜなかったのは、計画・締め・打刻・通知が予定の表と回の一覧を前提にしていて、
  混ぜると「数えない」の分岐を全部に足すことになるため。別に引けば、数えないことが形で保証される
- 展開して回で持つのは、読み込むたびに丸ごと入れ替える前提なら、外の RRULE を WBS の繰り返しの規則（ADR-0007）へ
  写す必要が無く、Outlook・Google の方言（タイムゾーン・この回だけの変更・消した回）をライブラリに任せられるため。
  期間の外は、購読なら次の読み込みで、ファイルなら書き出し直しで足る
- 購読しない URL を保存しないのは、持ち主の不安（Outlook の公開）に対し「読んだら公開を止める」を選べるようにするため。
  購読する URL を封じるのは、DB とその退避だけが漏れても URL が読めないようにするため（鍵は別の Secret にある）

## 影響

- 移行 `0015`（`down_revision` は `0014`）。下げると 2 つの表と取り込んだカレンダーの行が消える
- 依存に `icalendar` と `recurring-ical-events` を足した
- 配備は `CALENDAR_FEED_KEY_FILE` を足さないと購読できない（deploy-repo で鍵の Secret を作ってマウントする）
- 取り込んだ回の通知（アラーム）は出さない。要るなら別に決める
- WBS → 外への書き出し（ICS の配信）はしない（持ち主が不要と判断）
