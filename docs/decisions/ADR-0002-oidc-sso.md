# ADR-0002: IdP との連携は OIDC 認可コードフロー（PKCE）で行う

- 状態: 承認
- 日付: 2026-08-30

## 背景

これまで本アプリに認証は無く、全 API が `USER_ID = 1` 固定で動いていた
（`src/presentation/api/routers/*.py`）。手元やイントラの単独利用では成り立つが、
組織で使うには「誰が使っているか」を IdP に委ねられる必要がある。

社内には既に IdP（Keycloak / Microsoft Entra ID など）があり、そこで
パスワード・MFA・退職時の失効が一元管理されている。アプリ側で認証情報を
持つと、この管理から外れた二つ目の入口を作ることになる。

## 決定

**OpenID Connect の認可コードフロー（PKCE 付き）で IdP と連携する。**

- 本アプリはパスワードを保存しない。本人確認は常に IdP に委ねる。
- 利用者の同一性は `(iss, sub)` の対で決める（`federated_identities` テーブル）。
- ログイン後は自前の不透明なセッショントークンを HttpOnly Cookie で持たせ、
  DB には SHA-256 ハッシュだけを保存する（`auth_sessions`）。
- `AUTH_MODE` 環境変数で `single_user`（既定・従来動作）と `oidc` を切り替える。

## 理由

- **なぜ OIDC か**: SAML も候補だが、SPA + JSON API の構成では XML 署名の検証と
  POST バインディングの受け口が余分な重さになる。対象 IdP はいずれも OIDC を
  出しており、ディスカバリ文書で設定を自動取得できる。
- **なぜ認可コードフローか**: インプリシットフローはトークンが URL 断片に出て
  履歴・Referer から漏れる。認可コード + バックチャネルのトークン交換なら、
  トークンがブラウザを通らない。
- **なぜ PKCE を付けるか**: 認可コードは IdP からブラウザ経由で戻るため、
  リダイレクト履歴や共有端末のログから拾われうる。verifier を持たない相手には
  コードを渡してもトークンに換えられない。confidential client（client_secret あり）
  でも二重の守りとして常に付ける。
- **なぜ ID トークンをそのままセッションに使わないか**: ID トークンは失効させ
  られない。手元のセッションなら、退職・利用停止の反映をその場でできる
  （`SessionAuthenticationUseCases.authenticate` は毎回 `is_active` を見る）。
- **なぜ `(iss, sub)` で突き合わせるか**: メールアドレスは IdP 側で改姓・異動に
  伴って変わり、再利用されることもある。鍵にすると同じ人が別人になり、
  最悪の場合は別人が前任者のデータを引き継ぐ。
- **なぜセッショントークンをハッシュで保存するか**: DB のバックアップやダンプが
  そのままログイン手段にならないようにする。トークン自体が 256 ビットの乱数なので、
  パスワードのようなストレッチは不要。

## 影響

- 全 API が `CurrentUserDep` を経由するようになり、データは利用者ごとに分かれる。
  既存の単独利用配備は `AUTH_MODE` を設定しなければ従来どおり動く。
- `httpx` と `pyjwt[crypto]` がランタイム依存に加わる。
- IdP 側に本アプリをクライアントとして登録し、リダイレクト URI を許可する運用が
  必要になる（手順は `README.md`）。
- 初回ログイン時の自動作成（`OIDC_AUTO_PROVISION`）を有効にしたまま、テナント共用の
  IdP（Entra ID の common エンドポイントなど）を指すと、認証さえ通れば誰でも入れる。
  `OIDC_ALLOWED_EMAIL_DOMAINS` での絞り込みを併用する。
- 「複数利用者が同じタスクを共有する」機能は本 ADR の範囲外。今回入るのは
  「誰のデータか」の分離までで、共有・権限（ロール／スコープ）は別途決める。
