# ADR-0031: 予定・打刻の知らせを Web Push で端末へ送り、打刻アプリは予定の通知を自分で鳴らす

- 状態: 承認
- 日付: 2026-10-02
- 関連: task #193、ADR-0021（予定の通知と打刻アプリの「この先の通知」。**変えない**）・ADR-0025（定常業務）・
  ADR-0012（締め）・ADR-0018（打刻アプリの Bearer）・ADR-0028（PWA と自前の Service Worker。**その上に載せる**）、
  雛形 fastapitemplate の ADR-0047（Web Push）・ADR-0049（FCM）

## 背景

持ち主の依頼（2026-10-02、task #193）: 予定・打刻のプッシュ通知。送るもの（案）は、予定の通知（#183 で戻した
アラーム）・打刻の止め忘れ（走りっぱなし n 時間）・定常業務（#190）の回の開始・締めの時期（期間が終わった翌朝、
未確定があれば）。押したら該当の画面へ。設定画面で種類ごとに入り / 切り、端末ごとの登録。

WBS の事情:

- PWA（ADR-0028）で、Service Worker は自前（`frontend/src/serviceWorker/sw.ts`）。依存を足すと lockfile の作り直しが要る
- 打刻アプリ wbstimer（Android）は、`GET /api/calendar/alarms` で「この先の通知」を引き、端末で時刻どおりに鳴らす
  （ADR-0021。#182 の決定で **FCM は使わない**）
- 定期実行の足回りは API のプロセスの中の `IntervalWorker` だけ（`sso-reconciliation` が使う）。web は複数のワーカーで動く
- 雛形の Web Push（ADR-0047）は `pywebpush` を使い、お知らせを管理者が送る形。予定の時刻で自動で送る仕組みは無い

## 決定

### 1. サーバが送るのは Web Push だけ。依存を足さずに書く

- 届け先はブラウザ・PWA の購読（`push_subscriptions`）。送り口 `WebPushSender`（`src/infrastructure/push/`）は
  雛形と同じ振る舞い（404 / 410 の購読は外す・それ以外の失敗は残す・鍵ファイルが無くても作り直さない）で、
  **`pywebpush` を入れず**、既にある `cryptography`（`pyjwt[crypto]` が連れてくる）・`pyjwt`・`httpx` で書いた:
  中身の暗号化は RFC 8291（`aes128gcm`、1 レコード）、送り手の名乗りは RFC 8292（VAPID、ES256 の JWT）。
- 中身は JSON `{title, body, url, tag, kind}`。Service Worker が通知を出し（`tag` で同じ通知を置き換える）、
  押されたら `url`（このアプリの中のパスだけ。ほかは「今日」）を開く。開いている画面があればそれを手前へ出して移す。
- 預ける時間（TTL）は 1 時間。

### 2. 送るもの（種類）と時刻

判定は純関数 `PushNoticePlanner`（`src/application/push_notice_planner.py`）。時刻の来た通知は、遅れても
**5 分（`DUE_GRACE`）までは送る**。それより遅れたら送らない。

| 種類 `kind` | いつ | 押すと | 同じ通知の鍵 |
|---|---|---|---|
| `event_alarm` 予定の通知 | 予定のアラームの設定どおり（開始の 15 / 5 / 1 / 0 分前。ADR-0021 と同じ展開）。終日の回は送らない。同じ回で同時に送れるものが重なったら開始に近い 1 つだけ | `/calendar` | `<event_id>:<開始>:<分前>`（ADR-0021 の `id` と同じ形） |
| `routine_start` 定常業務の開始 | 分類がタスクの予定（ADR-0025）の回の開始。終日の回は利用者のその日の 8:00。アラームが無くても送る | `/`（今日） | `<event_id>:<開始>` |
| `timer_left_running` 打刻の止め忘れ | 走っている打刻が設定の時間（既定 4 時間、1〜24）を超えたら、1 本につき 1 回。7 日より前に始まった打刻は送らない | `/` | 打刻の id |
| `closing_due` 締めの時期 | 期間が終わった翌朝（新しい期間の初日の 8:00 以降、その日のうち）に、未確定の期間があれば | `/closing?period=<いちばん古い未確定>` | 新しい期間の初日 |

- **定常業務の回の開始と、その予定の「開始時刻」のアラームは同じ時刻なので 1 通にまとめ**、定常業務の通知として出す
  （定常業務を切っていれば予定の通知の「開始時刻」として出す）。
- 文言は利用者の言語（`ja` / `en`）でサーバが作る。日時は利用者のタイムゾーン。

### 3. 打刻アプリとの役割分担: **Web は Web Push、wbstimer は予定の通知を自分で鳴らす。二重に鳴らさない**

- **wbstimer は今のまま**（ADR-0021。`/calendar/alarms` を引いて端末で鳴らす）。WBS は wbstimer へ FCM で送らない
  （#182 の「FCM は使わない」を変えない）。
- 同じスマホで PWA の通知を受け、wbstimer も入れていると、予定の通知が 2 回鳴る。サーバからはブラウザの購読が
  どの端末のものか分からないので、**購読ごと（端末ごと）に「予定の通知もこの端末へ」（`receives_calendar`）を持ち**、
  wbstimer で鳴らしている端末では切ってもらう。切っても、予定から出ない種類（止め忘れ・締めの時期）は届く。
  予定から出る種類は `event_alarm` と `routine_start`（`PushKind.comes_from_calendar`）。
- wbstimer にも止め忘れ・締めの時期を出したくなったら、別の課題にする（wbstimer が打刻の状態から自分で鳴らすか、
  雛形 ADR-0049 の FCM を足すか。FCM なら鍵（サービスアカウント）と端末のトークンの登録の口が要る）。

### 4. 送る係: API のプロセスの定期処理（`push-dispatch`、60 秒ごと）

- `IntervalWorker`（`sso-reconciliation` と同じ形。`src/presentation/api/push_dispatch.py`）。起動の 20 秒後と、以後 60 秒ごと。
  **鍵が無い配備では起動しない**。
- 1 周回: 古い送った記録（30 日より前）を消す → 購読を持つ利用者ごとに（止めた利用者は飛ばす）、設定と事実
  （今日の前後 1 日の予定の回・走っている打刻・未確定の締めの期間）から送る通知を決める → 送る。
- 宛先は**その通知の持ち主の購読だけ**。種類を切っていれば決めない。`receives_calendar` を切った購読へは
  予定から出る種類を送らない。

### 5. 同じ通知を 2 度送らない記録（`push_dispatches`）

- `(user_id, kind, notice_key)` を一意にした表。**送る前に行を書いて確定し**、書けたプロセスだけが送る。web の
  ワーカーが複数でも、同じ周回が重なっても 1 度だけ出る。
- 送るのに失敗しても送り直さない（遅れた予定の通知は意味が無い。予定は画面とアプリにもある）。
- 行は 30 日で消す（鍵の時刻がそれより古い通知は二度と来ない）。

### 6. 設定と購読の口（Web のセッション Cookie だけ）

- `GET /api/push/config`（送れる配備か・公開鍵）、`GET` / `PUT /api/push/preferences`（種類ごとの入り / 切り・止め忘れの時間。
  省いた欄は今のまま。行が無い = すべて入り・4 時間）、`GET` / `POST /api/push/subscriptions`・
  `PATCH` / `DELETE /api/push/subscriptions/{id}`（購読の一覧・登録・`receives_calendar`・外す）。
- 送れない配備は購読を受け取らない（409）。他人の購読は「無い」（404）。同じ送り先を別の人が登録したら後の人の購読になる。
- ⚠ **送り先（`endpoint`）はサーバが POST する URL なので、https で、通知サービスのホストのものだけ受け取る**
  （`fcm.googleapis.com`・`push.services.mozilla.com`・`notify.windows.com`・`push.apple.com` とその下。既定のポートだけ）。
  `p256dh`（65 バイト）・`auth`（16 バイト）も形を確かめる。
- 一意は `endpoint` の sha256（`endpoint_hash`）に張る（MariaDB の索引の長さ。雛形と同じ）。

### 7. 画面（設定 → 「端末への通知」）

- 「この端末で受け取る」で通知の許可を求め、サーバの公開鍵で購読して登録する（公開鍵が替わっていれば古い購読を捨てる）。
  「この端末で止める」は登録を外し、ブラウザの購読もやめる。
- 知らせるもの（4 種類の入り / 切りと止め忘れの時間）、受け取る端末の一覧（名前・登録日時・最後に送った日時・
  「予定の通知もこの端末へ」・外す）。
- **開いただけでは登録し直さない。** 別の端末から「外す」を押した端末へは、その端末で押し直すまで送らない
  （ブラウザに購読が残っていても、一覧に無ければ「受け取っていません」と出す）。

### 8. 秘密と既定

- 鍵は値ではなく場所で持つ: `WEB_PUSH_VAPID_PRIVATE_KEY_FILE`（P-256 の秘密鍵の PEM）と `WEB_PUSH_SUBJECT`
  （`mailto:` か `https:`）。**どちらかが空、または鍵が読めなければ送らない（既定は閉じる）**。その間もアプリは動き、
  画面は「このサーバーでは使えません」を出す。作り方は `docs/OPERATIONS.md`。
- ⚠ 鍵を替えると、いまある購読はすべて届かなくなる（各端末で「この端末で受け取る」を押し直す）。

## 理由

- **サーバから押す（Web）**: ブラウザは閉じていると時刻を数えられない（Service Worker は常駐しない。
  Notification Triggers は標準にならなかった）。予定の時刻に端末を鳴らすには、サーバが時刻に送るしかない。
- **依存を足さない**: `pywebpush` は `requests`・`aiohttp`・`py-vapid`・`http-ece` を連れてきて、`uv.lock` の作り直しが要る。
  やることは「ECDH ＋ HKDF ＋ AES-GCM で包む」「ES256 で署名する」の 2 つで、既にある部品で 100 行ほど。
  ADR-0028（Service Worker を自前で書いた）と同じ判断。試験は受け手の側の復号で確かめる。
- **wbstimer へ FCM で送らない**: wbstimer は電波の無いところでも鳴るよう、先の分を端末に積む作り（ADR-0021）。
  FCM で同じ通知を送ると、アプリ側で二重を消す仕組みが要り、鍵（サービスアカウント）も増える。止め忘れ・締めは
  打刻の画面・締めの画面でも気付けるので、急がない。
- **端末ごとの `receives_calendar`**: 種類ごとの設定は人ごとなので、「PC のブラウザでは予定の通知が欲しいが、
  スマホは wbstimer が鳴らす」を表せない。購読（端末）に 1 つ持てば表せる。
- **送る前に記録する（決定 5）**: 送ってから書くと、2 つのワーカーが同時に送ってしまう。書いてから送ると、
  送るのに失敗した通知は二度と送られないが、予定の通知は遅れると意味が無いので、二重に鳴るより良い。
- **5 分の猶予**: 周回の間隔（60 秒）より十分長く、1〜2 周回落ちても拾える。それより遅れた通知は出さない
  （再起動のあとに、過ぎた予定の通知がまとめて鳴らない）。
- **送り先を通知サービスに限る**: 利用者が任意の URL を登録できると、サーバに内向きの URL を叩かせられる（SSRF）。
  主要なブラウザの通知サービスのホストは決まっている。

## 影響

- 移行 `0012`（`push_subscriptions`・`push_preferences`・`push_dispatches`）。
- 配る側に要るもの: VAPID の秘密鍵（ファイル）と `WEB_PUSH_SUBJECT`。無ければ通知は出ないだけで、ほかは今のまま。
- API のプロセスが 60 秒ごとに、購読を持つ利用者の数だけ予定の展開（3 日分）を行う。人数が増えて重くなったら、
  間隔を延ばすか、送る係を別のプロセスに分ける。
- iPhone・iPad は、ホーム画面に追加した WBS からでないと Web Push を使えない（Safari の制約）。
- 確かめられるのは本番の束だけ（Service Worker は `vite build` でしか焼かれない。ADR-0028）。CI は判定・暗号化・
  購読の流れの試験まで。
