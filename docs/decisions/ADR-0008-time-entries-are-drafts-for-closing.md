# ADR-0008: 打刻（Start / Stop）は下書きの表 `time_entries` に持つ

- 状態: 承認
- 日付: 2026-10-01
- 関連: task #154（打刻）・#152（器と実績の正本の決定）・#163（締めの規則の決定）・#161（締め）・#167（打刻アプリ）

## 背景

普段の記録を Start / Stop の 2 つだけにし（#154）、月 2 回の締め（#161）でまとめて直して確定する。
#152 で「打刻は**下書き**、締めで確定したものが `work_logs` になる」、#163 で締めの規則
（1〜15 日 / 16 日〜末日・区切りは利用者のタイムゾーンの 0:00・日をまたぐ打刻は 0:00 で割る・
確定後は読み取り専用で本人が開け直せる・丸めない）が決まっている。

締めの画面より先に配ってデータを溜め始めたいので、この段では表・API・上部のボタンまでを入れる。

## 決定

### 表 `time_entries`

| 列 | 中身 |
|---|---|
| `user_id` | 持ち主 |
| `started_at` / `ended_at` | naive な UTC。`ended_at` が空の間は「走っている」 |
| `task_id` | 空でよい（未割当でも記録が残ることを優先） |
| `memo` | 任意 |
| `source` | `timer` / `manual` / `split`（文字列。ネイティブ ENUM にしない）。今の段で作るのは `timer` だけ |

- **走っている打刻は 1 人 1 本**を、アプリ（Start は前を止めてから始める）と DB の両方で守る。
  DB は部分一意索引 `uq_time_entries_running_per_user`（`user_id`、`WHERE ended_at IS NULL`）。
  同時に 2 回 Start が来ても 2 本目は索引に当たり、409 になる。
  ⚠ 部分索引は SQLite（本番）と PostgreSQL の書き方で宣言している。MariaDB は部分索引を持たないので、
  MariaDB へ移すときはここを作り直す（生成列 + 一意索引など）。
- 期間の索引 `ix_time_entries_user_id_started_at`。
- 消すのは物理削除（下書きなので履歴を持たない。確定したものは `work_logs` に残る）。
- 秒まで持つ（`DATETIME`）。#163 の「分で持つ」は、確定して `work_logs` へ写すときの単位として扱う
  （丸めない・表示だけ 15 分単位）。

### 締めとの関係（今は列を作らない）

確定済みの期間の打刻を書き換えさせない仕組みは**締めの段（#161）で足す**。今は `period_locked` の
ような列を作らない。見込みは**別表**:

- `closing_periods`（`user_id`・期間の始まりと終わり（利用者のタイムゾーンの日付）・確定の時刻・
  確定したときのタイムゾーン）を持ち、打刻の修正・削除・手での追加の前に「その時刻が確定済みの
  期間に入っていないか」をこの表で引く。
- 打刻の行に印を持たせない理由: 開け直し（#163）のたびに期間内の全行を書き換えることになり、
  「確定した」という事実の置き場が行に散らばる。期間の行 1 つを足す・消すだけで済む方がきれい。
  日をまたぐ打刻（期間の境目の 0:00 をまたぐもの）も、行ではなく時刻で判定すれば扱いが 1 つになる。
- 確定で作った `work_logs` の行にどの期間から作ったかを持たせ（開け直しで消して作り直すため）、
  `source=締め` も足す。どちらも #161 の移行で。

### API（`/api/time-entries`）

| 操作 | 口 | 振る舞い |
|---|---|---|
| Start | `POST /start` | 本文は空でよい。走っていれば**同じ時刻で前を止めて**次を始める（切り替え）。返すのは始めた方と止めた方 |
| Stop | `POST /stop` | 走っていなければ何もせず `stopped: null`（冪等。2 度押しても 200） |
| 現在 | `GET /current` | 走っている打刻と `server_now`（端末の時計がずれていても経過を合わせるため） |
| 一覧 | `GET ?start=&end=` | `[start, end)` に掛かる打刻。**オフセット付きの時刻のみ受ける**（`Z` / `+09:00`）。日をまたぐ打刻は両方の日に出る。走っている打刻は終わりが無いものとして扱う |
| 1 件 | `GET /{id}`・`PATCH /{id}`・`DELETE /{id}` | 締めの画面のため。送った欄だけを変える。終わりは始まりより後・未来の時刻は不可・止まった打刻を走っている状態へ戻すことは不可 |

- 他人の打刻は「無い」として 404（`owned_by`）。タスクも同じ利用者のものに限る。
- 応答の時刻は `UtcDatetime`（`Z` 付き）。各打刻に `task_title`・`duration_seconds`（走っている間は
  今まで）・`is_long_running`（12 時間超）を添える。
- 「今」は `clock.utcnow()` を 1 つの操作の中で 1 度だけ読む（切り替えで止めた時刻と始めた時刻を揃える）。

### Start の既定のタスク

#154 の順は **いまの予定のタスク → 直前の打刻のタスク → 未割当**。予定の表と API は並行して
作っている（task #156 の続き）ので、アプリケーション層に口だけを置いた:

- `src/application/ports/scheduled_task_lookup.py` の `ScheduledTaskLookup.task_scheduled_at(user_id, at)`。
  今は何も返さない `NoScheduledTask` を繋いでいる（`dependencies.get_time_entry_use_cases`）。
- 予定の表ができたら、`at` に掛かっている予定の回（`CalendarEventUseCases.list_occurrences` の結果）の
  `task_id` を返す実装を足し、そこへ差し替えるだけでよい。候補のタスクが消されていた・他人のものだった
  ときは次の候補へ進む（打刻の側で確かめ直す）。
- 「直前の打刻のタスク」は、**タスクの付いた**打刻のうち一番新しいもの（未割当の打刻は飛ばす）。
- 本文で `task_id: null` を送ると、既定を使わずに未割当で始める。送らなければ既定の順。

### 画面

全画面の上部（`Layout` の上端）に打刻ボタンを常に出す（`frontend/src/components/TimerButton.tsx`）。
止まっている間は「▶ 開始」と、タスクを選んで始める ▾。走っている間は タスク名（押すとその場で
変えられる。変えなくてよい）・経過時間・「■ 停止」。12 時間を超えたら色を変えて ⚠ を付ける
（止め忘れはその場では直させない。締めで直す）。スマホ幅ではページの題名を隠して場所を空け、
新規タスクはアイコンだけにする。押せる高さは 44px。

### アプリ（#167）から叩くには何が要るか（この段では実装しない）

> 2026-10-01 追記: ADR-0018 で入れた。⚠ 2（宛名を `aud` に載せる）は採れなかった —— assay は人のログインの
> トークンに `resource` を効かせない（assay の ADR-0042 決定 6）。代わりに `client_id` で見分ける。

今の認証は**セッション Cookie だけ**（`get_current_user`）。Flutter のアプリが同じ API を叩くには:

1. **Bearer を受ける口を足す。** assay の利用者のアクセストークンは JWT で、JWKS で署名・`iss`・
   `exp` を確かめられる（blobshare の `verify_machine_token` と同じ道具）。`sub` を
   `federated_identities`（`iss` + `sub`）で引いて利用者に直し、無効な利用者は弾く。
   機械のトークン（`sub_type=client`）は受けない。
2. **宛名（`aud`）を登録する。** 素のままだと `aud` は `<issuer>/userinfo` で、**どのアプリへ出した
   トークンでも通ってしまう**。assay の `/admin/resources` に WBS の宛名（例 `api://wbs`）を登録して
   アプリのクライアントへ貸し、アプリは `resource=api://wbs` でトークンを取る。WBS は `aud` を完全一致で見る。
3. **アプリのクライアントを assay に登録する**（公開クライアント・PKCE・リダイレクト URI はアプリの
   スキーム）。アクセストークンは 300 秒なので、更新トークンでの取り直しがアプリ側に要る。
4. **Cookie と Bearer の口を分けるかを決める。** blobshare は機械の口で Cookie へ落とさない
   （ログイン済みのブラウザから踏まれる CSRF を避けるため）。WBS は同じ打刻の API を両方から使うので、
   「`Authorization` があれば Bearer だけで判定し、Cookie へ落ちない」形にする見込み。
5. **押した時刻を送れるようにする**（#167 の「電波が無いときは溜めて、繋がったら送る」）。
   Start / Stop の本文に任意の `at` を足す（未来は不可・前の打刻より前は不可）。今の API は本文を
   足しても後方互換で、口を分ける必要は無い。

## 理由

- 下書きと確定を別の表にした（#152）: 普段の Start / Stop は雑でよく、締めで直してから確定するので、
  確定後の数字（`work_logs`）は打刻の出来に引きずられない。打刻し忘れた日は `work_logs` を手で書ける。
- 1 人 1 本を DB でも守った: Start はスマホ（PWA）とアプリの両方から押される見込みで、同時に来ると
  アプリの確認だけでは 2 本走りうる。走っている打刻が 2 本あると「どれを止めるか」が決まらない。
- Stop を冪等にした: 電波の悪いところで 2 度押されても、エラーではなく「もう止まっている」で返す。
- 切り替えを 1 つの操作にした: 止めて・始めるを 2 回の呼び出しにすると、間で落ちたときに空白ができる。
  1 つの確定（`UnitOfWork.commit()`）で 2 行を書く。
- 一覧をオフセット付きの時刻で受けた: 締めの期間は利用者のタイムゾーンの 0:00 で切る（#163）。日付で
  受けるとサーバがタイムゾーンを推し量ることになるので、画面が区切りの瞬間を決めて送る。

## 影響

- 移行 `0002_time_entries`（`down_revision = 0001`）。予定の表は `0003` を使う。
- 締め（#161）: `closing_periods` の表と、確定済みの期間への修正・削除・追加を断る検査、手での追加
  （`source=manual`）・分割（`split`）の口を足す。
- 予定（#156 の続き）: `ScheduledTaskLookup` の実装を足して `get_time_entry_use_cases` で差し替える。
- 打刻アプリ（#167）: 上の「アプリから叩くには何が要るか」の 1〜5。
