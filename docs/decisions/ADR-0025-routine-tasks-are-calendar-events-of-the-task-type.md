# ADR-0025: 繰り返しのタスク（定常業務）は、予定に「予定 / タスク」の分類を足して表す

- 状態: 承認
- 日付: 2026-10-01

## 背景

持ち主の依頼（2026-10-01、task #190。目的は #186）: 「毎日行う定常業務タスク、など繰り返しのタスクもほしい。
予定、タスクって分類を変えるだけでよい」。

予定（NolumiaScheduler の移植。ADR-0007・0009）はすでに繰り返し・営業日シフト・この回だけの例外・回の移動を
持つ。一方で WBS のタスクは 1 回きりのもので、繰り返しを持たない。打刻・締め（ADR-0008・0012）で実績を
確定するにはタスクが要る（未割当は確定できない）。移植元の `EventType` は自由入力の文字列で、#155 で
持ってこなかった。

## 決定

- 予定に **分類 `event_type`** を足す: `EVENT`（予定。既定）/ `TASK`（タスク）。ネイティブ ENUM にせず
  文字列の列（`calendar_events.event_type`、既定 `EVENT`）。繰り返しの仕組みはどちらも同じものを使う。
  ⚠ `kind`（単発 / 繰り返し）はすでにあるので、名前は `event_type`。
- **分類がタスクの予定は WBS のタスクに結ぶ**（`task_id` が要る。集約の不変条件で、無ければ 422）。
  編集画面で分類を「タスク」にしたら、既存のタスクを選ぶか、「同じ名前のタスクを作って結ぶ」（既定で入り）。
  作るのは保存の直前で、作ったタスクは入力に残す（予定の保存に失敗してやり直しても 2 つ作らない）。
  作るタスクのプロジェクト（ADR-0024）もその場で選べる（既定はサイドバーで絞っているプロジェクト、無ければ未分類）。
  作るのは根のタスクなので、子タスクの所属の規則（親と同じ）には当たらない。
- **回ごとの「済み」**を表 `calendar_event_completions` に持つ。回の鍵は例外・移動と同じ
  （予定の id ＋ 候補日 ＋ 系列の開始時刻。単発は日・時刻とも NULL）。行がある = 済み。
  `PUT /api/calendar/events/{id}/done`（`{occurrence: 回の鍵 | null, done}`）で付け外しし、回の一覧
  （`/calendar/occurrences`）の `is_done` に出す。
  - 予定の集約の外に置き、**予定の版を進めない**（済みは予定の中身ではない。別の画面で開いている編集を 409 にしない）
  - 付けられるのは分類がタスクの予定の、今ある回だけ（予定の分類は 422、飛ばした回・候補でない日は 404）
  - 移した回・営業日シフトした回は元の鍵のままなので、済みは回について回る（移動を取り消しても済みのまま）
  - 系列の開始時刻を変えたら、例外・移動と同じく済みの鍵も付け替える
  - 「この回だけ」を切り出したら、その回の済みは新しい単発へ移す。「この回以降」を分けたら、以降の済みは
    新しい系列へ移す（鍵の時刻は新しい系列のもの）。系列を終えた後ろの回・消した予定の済みは消す
  - ⚠ SQLite では外部キーの CASCADE を効かせていないので、予定を消すときはユースケースが先に済みを消す
- 画面:
  - 「今日」に「今日やること」のカードを足す（今日のタスクの分類の回。終日が先、あとは始まりの順。済みも残す）。
    チェックで済み、▶ で結んだタスクの打刻を始める（動いていれば切り替え）。無い日はカードを出さない
  - カレンダー（週・平日・月・日の一覧）と「今日」のグリッドで、タスクの分類のブロックにチェックの形の印を付け、
    済みは薄く・取り消し線。印を押すと済みを切り替える。ドラッグとの区別は既存の判定
    （`useWeekDrag.shouldSuppressClick`）。月表示のチップは印だけ（押すと日を選ぶのは今のまま）
  - 済みの切り替えは応答を待たずに見せ、失敗したら取り直して戻る
- 移行は `0008`（task #187 の `0007` の後）。

## 理由

- 「分類を変えるだけ」という持ち主の言葉どおり、繰り返し・例外・移動・通知を作り直さずに済む。タスク側に
  繰り返しを持たせると、移植した予定の仕組みを 2 か所で持つことになる。
- 回ごとの済みを予定の例外（`calendar_event_exceptions`）に混ぜると、済みを付けるたびに予定の版が進み、
  ドラッグや編集の楽観ロックと衝突する。別の表にすると衝突しない。
- タスクに結ぶのを必須にしたのは、打刻・締めで実績を確定するにはタスクが要るから（ADR-0012）。
  結ぶ手間は「同じ名前のタスクを作って結ぶ」を既定にして 1 操作にした。
- WBS のタスクの状態（完了）とは連動させない。定常業務のタスクは毎日の回が済んでも続くもの。

## 影響

- 既存の予定はすべて分類「予定」。API は分類を省くと作るとき予定・直すとき今のまま、なので古い呼び手
  （打刻アプリ・ドラッグ）はそのまま動く。
- 締め・実績の集計は打刻（結んだタスク）から出るので変わらない。済みの数を集計に使うのは後の課題。
