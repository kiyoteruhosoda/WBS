# ADR-0018: 打刻アプリは assay のアクセストークンで Start / Stop / 現在を叩く

- 状態: 承認
- 日付: 2026-10-01
- 関連: task #167（打刻アプリ）・#154（打刻）、ADR-0008（「アプリから叩くには何が要るか」の 1〜5）、
  ADR-0002（OIDC）・ADR-0003（停止の伝播）、fastapitemplate の ADR-0045（同じ形の元）、
  assay の ADR-0042 決定 6（人のトークンに宛名を載せない）・ADR-0056（寿命 300 秒）

## 背景

打刻アプリ（Android / Flutter、#167）は assay に直接ログインし（public client + PKCE）、WBS の打刻の API を
そのまま叩く。今の WBS の認証はセッション Cookie だけ（ADR-0002）なので、アプリが持っているトークンで
入る口が無い。ADR-0008 の末尾に要るものを 5 つ挙げてあった。そのうち 2（WBS の宛名を `aud` に載せる）は、
書いた時点の見込みと assay の実際が違った:

- assay は **人のログイン（`authorization_code` / `refresh_token`）では `resource` を受け付けない。**
  アクセストークンの `aud` は常に `{issuer}/userinfo` で、`resource` を送ると `/token` が `invalid_target` で断る
  （assay の ADR-0042 決定 6。2026-09-30 に「据え置く」と決め直してある）。宛名を貸せるのは
  `client_credentials`（機械のトークン）だけ。
- 同じ問題を、雛形（fastapitemplate の ADR-0045）と foodexpiryweb が先に解いている。`aud` の代わりに
  **`client_id` で「どのアプリへ出したトークンか」を見分ける。**

## 決定

1. **`Authorization: Bearer` で来た assay のアクセストークンを、次をすべて満たすときだけ受け取る。**
   - 署名が assay の JWKS で検証でき、`typ` が `at+jwt`、`iss` がディスカバリの発行者、
     `aud` が `{issuer}/userinfo`、期限内（`IdentityProvider.verify_access_token`）
   - **`client_id` が `APP_CLIENT_IDS` に載っている**
   - `sub_type` が**無い**（機械のトークンではない。値ではなく有無で見る）
2. **利用者は `(iss, sub)` の結び付き（`federated_identities`）で引く。ここでは利用者を作らない。**
   結び付きが無ければ 403（「Web で 1 度ログインして」）。無効にした利用者も 403。
   ⚠ 雛形（ADR-0045 決定 4）は初めて来た人を userinfo で作る・寄せるが、WBS は採らない（理由の 3）。
3. **受け取るのは打刻の 3 つの口だけ** —— `GET /api/time-entries/current`・`POST /start`・`POST /stop`。
   （⚠ ADR-0021 で読み取りの `GET /api/calendar/alarms` を 1 つ足した。）
   印は依存関数 `get_app_or_web_user`（`AppOrWebUserDep`）。ほかの口（一覧・修正・締め・タスク・設定）は
   これまでどおり Cookie だけ（`get_current_user`）。
4. **`Authorization` ヘッダーがあれば Bearer だけで決め、Cookie へ落とさない。** Bearer でない・壊れている・
   受け取れないトークンは、同じリクエストに有効な Cookie が付いていても 401。
5. **`APP_CLIENT_IDS` は環境変数だけ**（カンマ区切りか JSON の配列）。**空なら Bearer は 1 本も通さない**（既定）。
   `AUTH_MODE=single_user` では何も見ない（従来どおり初期ユーザー）。
6. **Start / Stop の本文に任意の `at`（押した時刻、オフセット付き）を足す。** アプリが電波の無いときに溜めた
   押下を、繋がってから押した時刻で送るため（`src/domain/value_objects/press_time.py`）。
   - 未来は 422。ただし **60 秒まで**は端末の時計のずれとして「今」に寄せる
   - **7 日より前**は 422（それより前は締めの画面で手で足す）
   - 秒未満は落とす
   - Start: 走っている打刻の始まりより前は 422。**走っている打刻と同じ時刻の Start は送り直し**とみなし、
     何もせずその打刻を返す。過去の時刻から始めると他の打刻と重なるなら 409
   - Stop: 走っている打刻の始まりより前は 422。走っていなければ従来どおり `stopped: null`
   - 確定済みの締めの期間に掛かれば従来どおり 409。送らなければ「今」（Web の画面は何も変わらない）

## 理由

1. **`aud` ではなく `client_id` で受け取りを決めた。** 人のトークンに宛名が載らない以上、`aud` を WBS の宛名で
   比べると 1 本も通らない。assay の宛名を人のトークンへ開けるのは、assay 自身が「宛名と scope の語彙を
   一緒に開ける話」として据え置いた（開け直すきっかけは「人の代理で他アプリの API を呼ぶ RP」。打刻アプリは
   WBS の API しか呼ばない）。`client_id` は assay が署名した値なので、別のアプリへ出したトークン
   （Wiki・photonest のアプリ等）はここで落ちる。`aud = {issuer}/userinfo` の検証も残す
   （管理 API 宛て・機械の宛名宛てのトークンをここで落とす）。
   ⚠ assay が人のトークンにも宛名を載せるようになったら、`aud` の比較先を WBS の宛名へ替える
   （`verify_access_token` の 1 か所）。`client_id` の照合はそのまま残す。
2. **口を 3 つに絞った。** アプリの役目は Start / Stop だけ（#167）。修正・削除・締め・タスクまで開けると、
   盗まれたアプリのトークンでできることがむやみに広がる。足すときは `AppOrWebUserDep` を付け替える。
3. **アプリの口では利用者を作らない。** WBS で利用者を作る・メールで寄せるのはログインの規則
   （`ProvisioningPolicy`：ドメインの許可・検証済みメール・寄せない既定）と、ID トークンの `nonce` 付きの
   往復の上に載っている。アプリの口でも作るには userinfo を引いて同じ規則を二重に持つことになり、
   入口が 2 つになる。打刻アプリは Web の補助（補正・締めは Web）で、Web を使わずにアプリだけ使う人は居ない。
4. **Cookie へ落とさない。** 落とすと、トークンの切れたアプリが同じ端末のブラウザの Cookie で通ってしまい、
   誰が何で押したかが分からなくなる。Bearer を持ってくる相手は Bearer で成否を知るべき。
   （ブラウザが勝手に付けるのは Cookie だけで、`Authorization` は付けない。Bearer の側が CSRF の入口になることは無い。）
5. **環境変数だけにした。** 誤って足すと別のアプリへ出したトークンが通る。載せる値は配る人（deploy-repo の宣言）が決める。
6. **押した時刻を本文で送る。** 送った時刻で記録すると、電波の無い場所での打刻が全部ずれる。Start の送り直しを
   無害にしたのは、アプリが応答を受け取り損ねて同じ押下を送り直すと、長さ 0 の打刻ができて前の打刻が止まるため。
   7 日の上限は「溜めすぎた押下」と「時計の狂い」を締めの画面に回すため（締めは半月ごと）。

## 影響

- **停止の伝播（ADR-0003）とアプリのトークン。** アクセストークンは自前のセッションの行が無いので、
  受け口・定期照合でセッションを消しても**手元に控えの無いトークンは止まらない**。止まるまでの上限は次のとおり:
  - assay で利用者を止めた・ログアウトした —— assay が更新トークンを断るので、**最大 300 秒**（アクセストークンの寿命）
  - 名簿から外れた（定期照合の `unknown`）—— 結び付きが外れるので**次のリクエストから** 403
  - ⚠ 定期照合の `blocked` —— セッションは消すが結び付きは残す（ADR-0003）。assay が更新トークンも断る止め方なら
    300 秒で止まるが、そうでなければアプリは通り続ける。すぐ止めるなら WBS の利用者を無効にする（次のリクエストから 403）
- 初回はアプリのログインの前に Web で 1 度ログインしてもらう（結び付きが無いと 403）。
- 配る側に要るもの: `APP_CLIENT_IDS`（アプリの assay の public client の `client_id`）。手順は `docs/OPERATIONS.md`。
- 既存の試験で `get_current_user` を差し替えて「他人」として打刻を叩くものは、`get_app_or_web_user` も差し替える。
