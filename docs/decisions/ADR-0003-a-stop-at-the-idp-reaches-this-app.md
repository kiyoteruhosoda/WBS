# ADR-0003: IdP で止めた人は、このアプリでも止まる（受け口 ＋ 定期照合）

- 状態: 承認
- 日付: 2026-09-20
- 関連: ADR-0002（OIDC 認可コードフロー）

## 背景

ADR-0002 は「退職・利用停止の反映をその場でできる」ことを、ID トークンを直接使わない
理由として挙げている。⚠ **だがその反映は、こちらから IdP へ聞きに行く経路が無いかぎり
起きない。** 実際には次のようになっていた。

- ログイン後のセッションは自前の行（`auth_sessions`）で、**IdP を引かずに**更新される
- 毎リクエストで見るのは `users.is_active` ——これを落とすのは**このアプリの管理操作**で、
  IdP 側の停止とは別
- ⚠ **back-channel logout の受け口が無い**

⇒ **IdP で止めた人が、セッションの寿命（既定 12 時間）のあいだ入れたままになる。**

同じ IdP を使う他の 6 本は、受け口と定期照合の二段で塞いである。ここだけが二段とも無い。

## 決定

**「届いたら止める」（受け口）と「毎時聞き直して止める」（定期照合）の二段を入れる。
止めるのはこのアプリのセッションだけで、利用者（`users`）には触らない。**

### 1. 受け口 —— `POST /api/auth/backchannel-logout`

- OpenID Connect Back-Channel Logout 1.0。⚠ **未認証で叩ける口**で、相手の証明は
  `logout_token` の署名だけ。通らないものは**理由を返さずに** 400
- 宛名は `(iss, sub)` と、あれば `sid`。⚠ **`sid` がある通知は、その IdP のログインから
  始まったセッションだけを終わらせる**（よその端末のサインアウトで全部落とさない）
- ⚠ **再送では消さない。** 送り手は再送でも同じ `jti` を使う。効かせ直すと、IdP で戻して
  入り直した直後の再送が**新しいセッション**を落とす。受けた `jti` を
  `auth_backchannel_logout_deliveries` に残して弾く（1 日で片付ける）
- ⚠ **`users.is_active` は落とさない。** 止めたのは IdP であって、この口座の持ち主ではない。
  IdP で戻せば、こちらでは何もしなくてよい

### 2. 定期照合 —— 毎時、IdP に名簿を聞き直す

```
GET {OIDC_ISSUER}/admin/applications/self/users?subs=<結び付いている sub を 100 件ずつ>
Authorization: Bearer {MACHINE_CLIENT_ID で client_credentials ＋ resource={issuer}/admin}
```

| `state` | こちらの扱い |
|---|---|
| `allowed` | 触らない |
| `blocked` | その人の**セッションをすべて終わらせる**。⚠ 結び付きは残す |
| `unknown` | 同じく終わらせる ＋ **結び付き（`federated_identities`）を外す** |
| 知らない値・名簿に無い | **何もしない** |

- ⚠ **経路にアプリを書かない。** どのアプリの名簿かは、名乗ったサービスアカウントから
  IdP が決める
- ⚠ **引けなかったら何もしない。** 404・5xx・タイムアウト・トークンが取れない ——どれも
  「全員辞めた」ではない。⚠ **403 は「このサービスアカウントがまだアプリに結び付いて
  いない」**（準備待ち）なので警告にせず、情報を 1 行残して見送る
- ⚠ **全員が `unknown` なら何もしない。** 結び付きが 2 件以上あって全員が `unknown` なら、
  テナントの取り違えやアプリの付け替えを疑って見送る（警告）。1 件だけのときは
  「その 1 人が消えた」と区別が付かないので通常どおり扱う
- **web のプロセスで動く**（起動の 60 秒後と、その後 1 時間ごと）。このアプリには他に
  定期実行の足回りが無く、IdP と話す鍵を持っているのも web だけ。⚠ **ワーカーの数だけ
  同じ周回が走る**ので、照合は何度走らせても結果が変わらないように書く

### 3. 機械としての名乗りは `MACHINE_CLIENT_ID`（新設）

- IdP で**このアプリのサービスアカウント**として登録した `client_id`。ログイン用の
  `OIDC_CLIENT_ID` とは別の登録
- ⚠ **方式は常に `private_key_jwt`。** ログイン用のクライアントは public ＋ PKCE で鍵を
  持たず、`client_credentials` を使えない。鍵は `MACHINE_PRIVATE_KEY_FILE`（＋ `..._KID`）
- **空なら照合は走らない。** 受け口は名乗りが無くても効く（相手から来るので）
- ⚠ **名前に用途を書かない**（`RECONCILE_…` にしない）。IdP へこちらから問い合わせる
  名乗りは、この先も 1 つで足りる

## 理由

- **セッションが DB の行なので、消せばその場で効く。** 手元に控えの無いトークンを配って
  いないぶん、他の RP のような「失効を記録して次の更新で弾く」手当ては要らない。
  ⇒ **止まるまでの上限は「次のリクエスト」**
- **二段にするのは、受け口が届いたときにしか効かないから。** 送り先の未登録・送信の失敗・
  こちらの停止 ——どれも受け口だけでは取りこぼす。実際、同じ IdP で送り先の登録が
  2026-09-16 まで 0 件だった
- **利用者に触らないのは、止めた主体が違うから。** IdP の停止は「IdP で認証させない」で
  あって、このアプリの口座を消す判断ではない。戻すのに管理者の手が要らないのも利点

### 捨てた案

- **`users.is_active` を落とす。** 戻すのに管理者の手が要る（IdP で戻しても戻らない）。
  停止の主体と口座の持ち主を混ぜることになる
- **アクセストークンを短命にして寿命で切る。** このアプリはアクセストークンを配っていない
- **`sid` を見ずに常に利用者単位で止める。** 1 台のサインアウトで全端末が落ちる
- **受け口だけ / 照合だけ。** どちらも片方では取りこぼす（上記）
- **照合を cron や別プロセスへ出す。** 足回りを 1 つ増やすことになる。定期実行が他に無く、
  鍵を持つのが web だけである以上、いまは web の中で回すのがいちばん少ない

## 影響

- **設定が 4 つ増える**: `MACHINE_CLIENT_ID` / `MACHINE_PRIVATE_KEY_FILE` /
  `MACHINE_PRIVATE_KEY_KID` / `OIDC_LINK_BY_EMAIL`（ADR-0004）。
  ⚠ **compose の `environment:` にも足すこと**（`tests/unit/scripts/test_auth_env_passthrough.py`）
- **表が 1 つ・列が 1 つ増える**: `auth_backchannel_logout_deliveries` と
  `auth_sessions.idp_session_id`。どちらも起動時に作られる（既存の行は `NULL` のままでよい）
- ⚠ **有効にするには IdP 側の 3 手が要る**: ①このアプリの `backchannel_logout_uri` を
  `https://<host>/api/auth/backchannel-logout` で登録、②サービスアカウントを登録
  （`client_credentials` ＋ このアプリの公開鍵）、③アプリの「このアプリの名乗り」に結び付ける。
  手順は `docs/OPERATIONS.md`
- ⚠ **`sid` を出さない IdP では、停止は利用者単位でしか効かない**（その人の全セッションが終わる）
